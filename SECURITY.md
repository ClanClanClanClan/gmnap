# Security policy

## Supported versions

The project is pre-tagged-release; the `main` branch is the only
supported version. Security fixes land directly on `main` and are
shipped immediately as new commits — no separate release cadence
exists yet.

If you're running an old commit, please update before reporting an
issue, since I may already have fixed it.

## Reporting a vulnerability

**Do not open a public GitHub Issue or pull request for security
vulnerabilities.** Disclosing publicly before a fix is in place puts
every running instance at risk.

Email reports to **dylan.possamai@math.ethz.ch** with the subject
line:

```
[SECURITY] gmnap: <one-line summary>
```

Include in the body:

- a description of the issue, severity in your judgement, and
  affected components (API endpoints / CLI commands / pipeline
  stages);
- step-by-step reproduction (smallest input that triggers it);
- a guess at the impact (data leak, RCE, DoS, GDPR violation,
  rate-limit bypass, etc.);
- whether you've already disclosed it elsewhere or to whom.

If you can include a proof-of-concept patch, even better — but
don't push it as a PR; attach it to the email.

## What you can expect

- Acknowledgement within **5 business days** of receipt.
- Triage decision within **15 business days** — confirmed vs.
  not-a-vulnerability vs. need-more-info.
- For confirmed issues: a coordinated-disclosure plan including a
  fix-availability target. Default disclosure window is **90 days**
  from acknowledgement, extensible by mutual agreement if the fix
  is genuinely complex.
- Public credit in `CHANGELOG.md` and the patch commit message,
  unless you ask to remain anonymous.

## What's in scope

- The `src/api/server.py` HTTP surface (every endpoint listed in
  `docs/api_reference.md`).
- The `src/cli/gmnap.py` CLI (input validation, command-injection
  guards in `gmnap process` etc.).
- The `src/pipeline/` data flow (deterministic-output guarantees,
  GDPR pipeline correctness, schema validation strictness).
- The `src/authority/` and `src/authorities/` enrichment paths
  (HTTP cache integrity, rate-limit / hashcash bypass).
- The `static/` web UI (XSS, CSRF, the hashcash worker, the d3
  tree renderer's input handling).
- Authentication / token handling for paid-tier API access.
- Container / `docker-compose.yml` defaults (privilege escalation,
  exposed ports, default credentials).

## What's out of scope

The following are documented limitations or operational concerns
that don't qualify for a vulnerability report:

- `OFFLINE=1` is the default for tier-1+ authority sources (per V7
  spec). Reports that this prevents lookups are not bugs.
- Rate limiting is per-process, not per-cluster — operating multiple
  replicas multiplies the effective limit. Documented behaviour, not
  a vulnerability.
- The free-tier hashcash proof-of-work is intentionally weak (18
  bits, ~1 s on a modern CPU). Bypass via custom client is not a
  bug; it's a polite-traffic mechanism, not a security control.
- Data-quality issues in `data/genealogy_enrichment.json` (e.g. a
  Wikidata-sourced birth year being off by a year). File a normal
  GitHub Issue for these.
- Theoretical cryptographic attacks against SHA-256 or AES-GCM at
  current key sizes. The algorithms are fine; if your report
  fundamentally depends on them being broken, it's not actionable.

## What I'll fix vs. document

If a report is confirmed:

- **High / critical** (RCE, auth bypass, GDPR-data exfiltration):
  fix on `main` ASAP; CHANGELOG entry; coordinated public disclosure
  on or before the agreed window.
- **Medium** (e.g. info disclosure of metadata, DoS via expensive
  endpoint): fix on `main` within the next 1-2 PRs; CHANGELOG entry.
- **Low** (e.g. an XSS sink that's only reachable with a malformed
  client): patched but may take longer; documented in CHANGELOG.

If I conclude a report isn't actionable, I'll explain why.

## Hardening already in place

(Not exhaustive — see `src/api/server.py` for the full middleware
stack.)

- Content-Security-Policy: `default-src 'self'; script-src 'self';
  style-src 'self'`.
- HSTS with `max-age=31536000; includeSubDomains`.
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`,
  `Permissions-Policy: geolocation=(), microphone=(), camera=()`.
- Rate limiting + hashcash on the public surface; Bearer-token gate
  on the paid tier.
- TruffleHog secret-scan on every push (`--only-verified`).
- 31-scenario adversarial Playwright harness in CI covering XSS,
  Unicode payload injection, server-500 mid-flight, rapid-fire,
  responsive viewports.
- Dependencies pinned via `requirements.lock` (regenerated by
  `make lock`); CI verifies the lockfile is in sync on every push.
- Memgraph integration test against a real container in CI.
